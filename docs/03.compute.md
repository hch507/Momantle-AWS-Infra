# Compute 설계

## 1. 설계 개요

EC2 기반 컴퓨팅 환경에서 Spring Boot와 FastAPI를 Docker 컨테이너로 운영한다.

앱 서버는 두 개의 가용 영역(ap-northeast-2a, ap-northeast-2b)에 걸쳐 구성하며, 인스턴스 장애 발생 시 Auto Scaling Group(ASG)이 대체 인스턴스를 생성하도록 설계했다.

두 서비스는 서로 다른 특성을 고려해 별도의 Auto Scaling 전략을 적용했다.

- **Spring Boot**: 스케줄러의 중복 실행을 방지하기 위해 단일 인스턴스로 운영하며, 장애 발생 시 ASG를 통해 인스턴스를 자동 복구한다.
- **FastAPI**: AI 기반 단어 유사도 연산으로 CPU 사용량이 증가할 수 있으므로, 부하에 따라 인스턴스를 수평 확장할 수 있도록 구성한다.

## 2. EC2 구성

| 구성 요소 | 역할 | 인스턴스 타입 | 비고 |
|---|---|---|---|
| Spring Boot EC2 | API 및 비즈니스 로직 처리 | 확인 필요 | 포트 8080 |
| FastAPI EC2 | AI 기반 단어 유사도 분석 | 확인 필요 | 포트 8000 |
| NAT Instance (AZ별 1대) | Private Subnet의 외부 통신 중계 | 확인 필요 | ASG 외부에서 개별 운영 |

- 서버 환경은 AMI와 Launch Template을 기반으로 동일한 인스턴스를 재생성할 수 있도록 구성한다.
- IAM 인스턴스 프로파일을 통해 EC2에 필요한 AWS 리소스 접근 권한을 부여한다.
- FastAPI 모델 파일은 S3에서 다운로드하여 인스턴스에 로딩한다.
- 서버 접속은 SSH 대신 SSM Session Manager를 사용하며, SSH 포트는 외부에 개방하지 않는다.

## 3. Load Balancer 구성

### External ALB

- Public Subnet(ap-northeast-2a, ap-northeast-2b)에 배치한다.
- 외부 클라이언트의 요청을 수신하여 Spring Boot 타겟 그룹으로 전달한다.
- 리스너 포트는 HTTP 80을 사용한다.
- Spring Boot 보안 그룹에서는 External ALB 보안 그룹에서 전달되는 8080 포트만 허용한다.

### Internal ALB

- App Private Subnet(ap-northeast-2a, ap-northeast-2b)에 배치한다.
- Spring Boot에서 발생한 AI 분석 요청을 수신하여 FastAPI 타겟 그룹으로 전달한다.
- 내부 통신 전용으로 구성하여 FastAPI 인스턴스가 외부에 직접 노출되지 않도록 한다.
- FastAPI 보안 그룹에서는 Internal ALB 보안 그룹에서 전달되는 8000 포트만 허용한다.

## 4. Spring Boot Auto Scaling

Spring Boot는 현재 스케줄러를 포함하고 있어 여러 인스턴스에서 동일한 작업이 중복 실행될 가능성이 있다.

이를 방지하기 위해 현재는 단일 인스턴스로 운영하고, 인스턴스 장애 발생 시 ASG가 대체 인스턴스를 생성하도록 구성한다.

| 항목 | 설정값 |
|---|---|
| Desired / Min / Max | 1 / 1 / 1 |
| 배치 서브넷 | App Private Subnet (2a, 2b) |
| 헬스 체크 유형 | ELB |
| 상태 확인 유예 시간 | 300초 |

- 인스턴스 장애 발생 시 ASG가 비정상 인스턴스를 교체한다.
- 두 AZ의 서브넷을 사용하므로 대체 인스턴스는 가용한 AZ에 생성될 수 있다.
- 단일 인스턴스 구조이므로 대체 인스턴스가 생성되고 정상 상태가 되기 전까지 서비스 중단이 발생할 수 있다.
- Desired / Min / Max가 모두 1이므로 수평 확장이 아닌 장애 복구를 목적으로 한다.

**향후 개선**

- ShedLock 등 분산 락을 적용하여 스케줄러의 중복 실행을 방지한다.
- 다중 인스턴스 운영이 가능하도록 개선하여 서비스 가용성을 높인다.

## 5. FastAPI Auto Scaling

FastAPI는 AI 기반 단어 유사도 연산으로 CPU 사용량이 증가할 수 있으므로, 트래픽과 CPU 부하에 따라 인스턴스를 확장할 수 있도록 구성한다.

| 항목 | 설정값 |
|---|---|
| Desired / Min / Max | 1 / 1 / 2 |
| 확장 정책 | 대상 추적(Target Tracking) |
| CPU 목표 사용률 | 60% |
| 배치 서브넷 | App Private Subnet (2a, 2b) |
| 상태 확인 유예 시간 | 300초 (실제 설정 확인 필요) |

- CPU 사용률이 목표치를 초과하면 Scale Out을 수행한다.
- 부하가 감소하면 Scale In을 수행한다.
- 새 인스턴스는 모델 파일을 다운로드하고 메모리에 로딩하는 초기화 과정을 거친다. //확인 필요//
- 모델 로딩이 완료된 후에만 `/health` API가 HTTP 200을 반환하도록 구성하여 준비되지 않은 인스턴스로 트래픽이 전달되지 않도록 한다.//확인 필요//
- 모델 로딩 시간을 고려하여 ASG의 상태 확인 유예 시간을 설정한다.//확인 필요//

## 6. Health Check

ALB의 Health Check를 통해 각 서비스 인스턴스의 정상 동작 여부를 확인한다.

| 대상 | Health Check 경로 | 간격 / Healthy 횟수 / Unhealthy 횟수 |
|---|---|---|
| Spring Boot | 확인 필요 | 확인 필요 |
| FastAPI | `/health` | 확인 필요 |

- ALB는 Health Check에 실패한 타겟을 정상적인 트래픽 전달 대상에서 제외한다.
- ASG의 헬스 체크 유형이 ELB로 설정된 경우, ELB 상태를 기반으로 비정상 인스턴스를 교체할 수 있다.
- FastAPI는 모델 로딩이 완료된 이후 정상 상태를 반환하도록 하여 초기화가 끝나지 않은 인스턴스로 요청이 전달되는 것을 방지한다.

## 7. 설계 특징 및 한계

### 설계 특징

- 두 개의 가용 영역을 활용한 멀티 AZ 기반 컴퓨팅 환경
- 서비스 특성에 따른 Spring Boot와 FastAPI의 Auto Scaling 전략 분리
- AMI와 Launch Template을 활용한 서버 환경 재현
- External ALB와 Internal ALB를 통한 외부 및 내부 요청 경로 분리
- SSM Session Manager를 활용한 안전한 서버 접속
- 필요한 최소 인스턴스 수를 유지하여 운영 비용 최적화

### 설계 한계 및 개선 과제

**1. Spring Boot 단일 인스턴스 운영**

- 현재 단일 인스턴스로 운영하므로 장애 발생 시 대체 인스턴스가 준비될 때까지 서비스 중단이 발생할 수 있다.
- ShedLock 적용을 통해 스케줄러 중복 실행 문제를 해결하고 다중 인스턴스 운영으로 개선할 예정이다.

**2. NAT Instance 장애 대응**

- NAT Instance는 AZ별로 1대씩 운영하며 ASG에 포함하지 않았다.
- NAT Instance 장애 발생 시 해당 AZ의 App Private Subnet에서 외부로 나가는 통신에 영향을 줄 수 있다.
- 장애 대응 자동화 및 NAT Gateway 전환 여부를 향후 검토한다.

**3. Auto Scaling의 AZ 배치**

- ASG는 여러 AZ에 걸쳐 인스턴스를 배치할 수 있지만, 특정 AZ를 항상 우선적으로 선택하도록 보장하지 않는다.
- AZ별 배치는 ASG의 가용 영역 분산 정책과 현재 리소스 상황에 따라 결정된다.

**4. 초기 인스턴스 구동 시간**

- FastAPI는 모델 파일 다운로드 및 메모리 로딩 과정이 필요하므로 인스턴스 생성 직후 바로 요청을 처리하기 어렵다.
- 모델 초기화 시간과 Health Check 설정을 지속적으로 검토하여 Scale Out 이후 서비스 투입 시간을 개선할 예정이다.
